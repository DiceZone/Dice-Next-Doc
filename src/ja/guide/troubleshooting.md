# トラブルシューティング

パスワードの復旧、手動設定、バックアップ、更新などは[よくある質問 FAQ](/ja/guide/faq)を参照してください。

問題が起きたら、このページの順に確認してください。問題を報告するときは、該当するログやクラッシュレポートのファイルをできるだけ添付してください。

## まずログを探す

| 内容 | 場所 |
|------|------|
| 動作ログ | `data/logs/app/dice-<起動時刻>-<プロセス ID>_<日付>.log`（起動ごとに新規作成し、日付が変わると自動で分割） |
| 構造化された診断情報 | 同じフォルダーにある同名の `.jsonl`。処理の発生元、関連する msgID、コードの位置、スレッドなどの詳細を記録します。こちらも機密情報は伏せられます |
| クラッシュレポート | `data/logs/crash_<時刻>.txt` |
| セッションログ | `data/logs/`（`.log` で出力した txt / html） |
| 監査ログ | `data/audit/`（通知システムのイベント記録、jsonl） |

コンソールウィンドウは既定で非表示です。タスクトレイのアイコンを右クリックしたメニューから、いつでも表示・非表示を切り替えられます。

ホーム画面のログは既定で INFO 以上を表示するため、通常のハートビートやポーリングで埋まることはありません。調査が必要なときは、まず WebUI 設定で「最低記録レベル」を下げ、次にホーム画面の「最低表示レベル」を下げてください。後者を下げても、記録されていなかったデバッグ情報は表示されません。送信の問題は msgID で検索し、`[处理]`（処理）の項目で発生元と送信予定の内容を、`[消息]`（メッセージ）の項目で実際の内容と失敗理由を確認できます。詳しくは[プログラムログ](/ja/manage/dashboard#プログラムログ)を参照してください。

## プログラムが異常終了する／「動作を停止しました」

Dice!Next にはクラッシュ診断の仕組みが組み込まれています。どのような種類のクラッシュ（アクセス違反、捕捉されない C++ 例外、CRT の無効なパラメーター、abort）でも、終了前に原因を **`data/logs/crash_*.txt`** に書き出します。内容は次のとおりです。

- 時刻、クラッシュの種類、バージョン / build 番号
- **起動段階の目印**（`main:chdir` / `config` / `database` / `running` など）。スタックトレースがなくても、どの段階で止まったかがわかります
- 例外コード、エラーが起きたアドレスの **モジュール名とオフセット**、捕捉されなかった例外の `what()` の文字列

確認の手順：

1. `data/logs/` にある最新の `crash_*.txt` を開き、`phase` と `kind` を確認します。
2. 同じ時刻の `data/logs/app/` の動作ログの最後の数行と照らし合わせます。
3. 問題を報告するときは、この 2 つのファイルを一緒に開発者へ送ってください。ほとんどの場合、それで原因を特定できます。

::: tip
`data/logs/` に書き込めない場合、レポートはプログラムフォルダーの `crash.txt` に書き出されます。
:::

## exe をダブルクリックしても「何も起きない」

まずプロセスが動作しているか確認してください。既定では **起動するとすぐタスクトレイに最小化** され（右下に通知が表示されます）、コンソールウィンドウは表示されません。

- タスクバー右下のトレイアイコンを探し、右クリックすると「Web パネルを開く／コンソールを表示／プログラムフォルダーを開く／終了」を選べます。
- 「起動時にコンソールを表示する」以前の動作に戻したい場合は、設定 `dice.console_start_hidden` を `false` にします。

## 2 つ目のプロセスが起動してすぐ終了する

同じデータ（同じ `data/` フォルダー）で **実行できるプロセスは 1 つだけ** です。起動時にデータフォルダーへ単一インスタンス用のロック `.instance.lock` を書き込み、既存のインスタンスを検出すると 2 つ目のプロセスはすぐに終了し、コンソールやログにメッセージを出します。2 つのプロセスが同時にデータベースへ書き込んで壊すのを防ぐためです。

- 複数のダイスボットを動かしたい場合は、プログラムフォルダーを丸ごとコピーし、それぞれ別の `data/` を使ってください。
- 同じデータを使うプロセスと自動再起動サービスを停止してから起動します。ロックは OS が管理するため、`.instance.lock` の削除で保護を回避しないでください。失敗が続く場合はログとディレクトリの権限を確認してください。

## WebUI が開かない

1. **プロセスが動いているか確認する**：トレイアイコンがあるか、`data/logs/app/` に新しいログが出ているかを確認します。
2. **ポートが変わっている可能性**：既定のポート `18088` が使用中の場合、**次の空いているポートへ自動で移り、設定ファイルに書き戻します**。起動ログには WARN が 1 行出ます。いちばん簡単なのは、トレイを右クリックして「Web パネルを開く」を選ぶ方法です。常に現在のポートが使われます。`config/server.json` の `port` でも確認できます。
3. **リモートからのアクセス**：`server.host` が `0.0.0.0` になっているか、ファイアウォールでポートが許可されているかを確認します。インターネットへ直接公開することはおすすめしません。[デプロイと運用](/ja/guide/deploy)を参照してください。
4. **ログインを求められる**：WebUI のログインパスワードを設定すると、すべての管理ページでログインが必要になります。ログイン時に「このデバイスを信頼する」にチェックすると、このマシンで 30 日間セッションが保たれます。

### WebUI のログインパスワードを忘れた

[パスワードの復旧手順](/ja/guide/faq#reset-password)に従って、外部アクセスの制限、停止、バックアップを行います。使用中の設定ディレクトリの `webui.json` で `password` を空にし、古い `webui_sessions.json` を削除してから起動し、新しいパスワードを設定してください。空のパスワードは初回設定の状態になり、認証が無効になるわけではありません。

## アダプターが接続できない

まず正方向と逆方向を区別します。

| モード | どちらが接続するか | エンドポイントの入力内容 |
|------|--------|-----------|
| 正方向 WS（`forward_ws`） | Dice!Next から OneBot クライアントへ **接続する** | OneBot クライアントの正方向 WS のアドレス（例：`ws://127.0.0.1:3001/`） |
| 逆方向 WS（`reverse_ws`） | OneBot クライアントから Dice!Next へ **接続してくる** | **ポート番号** だけを入力（例：`6700`）。そのうえで OneBot クライアントの逆方向 WS の接続先を `ws://<Dice!Next の IP>:<そのポート>/` に設定 |

順に確認してください。

- **OneBot クライアント**（NapCat / Lagrange / LLOneBot など）で対応するサービス（正方向 WS サーバー / 逆方向 WS の送信）が有効になっているか、ポートが一致しているか。
- **`access_token`** が両側で同じか（空にする場合は両方とも空にします）。正方向の接続では、Dice!Next は `Authorization: Bearer <token>` ヘッダーで送信します。
- **ファイアウォール**：逆方向モードでは Dice!Next が待ち受けるポートを許可し、正方向モードでは OneBot クライアントのポートに到達できる必要があります。
- **状態が「接続タイムアウト」**：正方向 WS は切断後に自動で再接続します（最初の 10 回は 5 秒ごと、11〜20 回目は 60 秒ごと）。20 回連続で失敗すると自動再接続を止めて「接続タイムアウト」になります。OneBot 側を直してから、アダプター管理ページで手動で再接続してください。
- ダッシュボードのリアルタイムログと `data/logs/app/` に具体的なエラーの原因が出ています。

## コマンドに返信しない

- グループで `.bot off`（グループでの停止）が送られていないか。[グループ管理](/ja/manage/groups)またはグループ内で `.bot on` を送ると元に戻せます。
- 全体のサイレントや全体でのコマンド停止が有効になっていないか（[基本設定](/ja/manage/settings)）。
- ユーザーやグループがブラックリストに入っていないか。
- ホワイトリストモード（`dice.whitelist_only`）では、ホワイトリストにないグループには反応しません。
- アダプターの状態が「接続済み」になっているか。
- QQ に接続せずにデバッグしたい場合は、管理パネルの **テスト台** で直接コマンドを送って返信を確認できます。

## それでも解決しない場合

次の情報を添えて報告してください。

1. バージョン / build 番号（管理パネルの「プロジェクトについて」ページ、または起動ログの 1 行目）
2. `data/logs/app/` の最新ログの該当部分
3. クラッシュの場合：`data/logs/crash_*.txt` の全文
4. 再現手順
