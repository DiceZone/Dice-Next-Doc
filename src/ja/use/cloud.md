# クラウドと本人確認

`.cloud` はアカウントセンターの認可の入口で、`.bind` は異なるプラットフォームのチャットを同じ本物の QQ に関連付けます。アカウントを紐付けるだけなら `.bind qq <あなたの QQ 番号>` で十分です。ボットが確認方法を自動で選ぶため、先にメールや OAuth のコマンドを覚える必要はありません。クラウドのキャラクターシートが必要になったら `.cloud` を使ってください。クラウドのシートの認可では本物の QQ もあわせて確認できますが、紐付けだけの認可ではクラウドのシートの読み書きの権限は与えられません。

## 紐付けが必要な理由

ボットがプラットフォームごとに受け取る識別子は異なります。OneBot は本物の QQ 番号を、QQ 公式ボットは分離された OpenID だけを渡し、Discord と KOOK にはそれぞれ独自のユーザー ID があります。紐付けがないと、同じ人がこれらのチャットでは別人として扱われ、キャラクターシート、好感度、能力値がそれぞれ別に保存されます。

紐付けると、これらは同じデータを指すようになります。公式のグループで記録したシートを、OneBot のチャットに戻ってもそのまま使えます。

## 紐付けのクイックスタート

QQ 公式ボット、Discord、KOOK の **個人チャット** で次のように送ります。

```text
.bind qq 160703953
```

例の番号は自分の QQ 番号に置き換えてください。ボットは **現在のクライアント** の設定に基づいて自動で選びます。

- **正式なボットのキーがある場合**：OAuth を優先し、アカウントセンターの認可 URL と認可コードを個人チャットで送ります。Web ページでログインして QQ の本人確認に同意し、元の個人チャットに戻って `.bind confirm` を送ります。
- **キーはないが、ダイスマスターが SMTP を有効にしている場合**：`あなたのQQ番号@qq.com` に確認コードを自動で送ります。元の個人チャットに戻って `.bind confirm <8 桁の確認コード>` を送ります。QQ 番号を入力し直す必要はありません。
- **どちらも設定されていない場合**：現在は使えないことをはっきり伝え、メールは送らず、紐付けも完了しません。ダイスマスターに設定を依頼するか、OneBot / Milky から逆方向に紐付けてください。

OAuth で認可したアカウントの確認済みの QQ は、**申請した番号と一致している必要があります**。番号が異なる場合、本人確認の権限を与えていない場合、アカウントがすでに別の QQ に紐付けられている場合は、紐付けを上書きできません。OAuth が失敗しても、黙ってメールに切り替えることはありません。ダイスマスターが SMTP を設定していれば、`.bind qq 160703953 email` を入力して自分で切り替えられます。切り替えた後はメールの確認コードで確認し、以前の OAuth の申請は無効になります。

申請と確認は、同じプラットフォームの同じユーザーから、同じクライアントの同じ個人チャットで行う必要があります。ボットの再起動後や申請の期限切れ後は、最初からやり直してください。

## クラウドのキャラクターシートのクイックスタート

ボットとの **個人チャット** で次のように送ります。

```text
.cloud auth
```

ボットが URL と確認コードを個人チャットで送ってきます。URL を開いてアカウントセンターのアカウントでログインし、どのボットが申請しているかを確認して認可に同意し、個人チャットに戻ります。

```text
.cloud confirm
```

「認可の準備ができました」と表示されれば完了です。返信にあなたの QQ 番号が含まれていれば、本物の QQ の確認と紐付けも完了しています。

::: tip 認可で QQ 番号を証明できる理由
アカウントセンターでは、登録時に数字だけの QQ メールアドレスしか受け付けず、メールの確認コードによる認証が必須です。そのため、登録メールアドレスの @ より前の部分は、確認済みの本物の QQ 番号になります。
:::

## `.cloud` コマンド

`.cloud` のコマンドはすべて個人チャットでのみ使えます。

```text
.cloud auth [write] // アカウントセンターの認可を申請。既定は読み取りのみで、write を付けると書き込みも申請
.cloud confirm // Web ページで確認コードを入力して同意した後、個人チャットに戻って確認
.cloud status // 現在の認可の状態を表示
.cloud logout // このボットに保存された認可を消去
.cloud list // クラウドのキャラクターシートを一覧表示
.cloud pull <クラウドのシート ID> [ローカルのシート名] // クラウドのシートをローカルに取得
.cloud push <ローカルのシート名> // ローカルのシートを初めてアップロード
.cloud sync <ローカルのシート名> // 前回同期した版に基づいて変更を送信
.cloud diff <ローカルのシート名> // 基準・ローカル・クラウドの項目を読み取り専用で比較。シートも同期の基準も変更しない
```

### 読み取りと書き込み

同期で競合した場合は、まず `.cloud diff ローカルのシート名` を使います。各項目は「基準 | ローカル | クラウド」の順に並び、`local` はローカルだけの変更、`remote` はクラウドだけの変更、`same` は両側で同じ変更、`conflict` は両側で異なる変更を表します。表示は最大 30 項目です。長い値は `.cloud pull クラウドのシート ID 新しいシート名` で別のコピーを取得して比べられます。この入口は本人の個人チャット専用で、読み取りロックを回避したり、シートを上書きしたり、同期の基準を進めたりすることはありません。

自動同期と項目ごとの競合の編集はまだ設計中で、有効になっていません。現在の認可は自動アップロードへの同意を意味するものではなく、トークンの期限切れや再起動の後は引き続き認可し直す必要があります。

既定では読み取りの権限だけを申請します。アップロードや同期が必要な場合は `.cloud auth write` を使い、Web ページでも書き込みに明示的にチェックしてください。両方で同意したときだけ有効になります。すでに読み取りのみで認可している場合は、もう一度 `.cloud auth write` を実行するだけです。

### 認可の範囲と有効期間

| 項目 | 説明 |
| --- | --- |
| 適用範囲 | 「アダプター + ボットのアカウント + プラットフォーム + あなた本人」ごとに区別され、グループとは関係ありません |
| 複数のアダプター | OneBot と QQ 公式を同時に使う場合は、それぞれで 1 回ずつ認可が必要です |
| 有効期間 | トークンはメモリ上にのみ保存され、ボットの再起動後やトークンの期限切れ後は認可し直す必要があります |
| ローカルのデータ | 認可し直しても、ローカルに取得済みのシートと同期の対応関係には影響しません |

::: warning 認可後にダイスマスターが見られるもの
認可に同意すると、そのボットはあなたがアカウントセンターに登録したときに確認された QQ 番号を読み取れるようになります。ボットの多くは第三者が独自に運用しており、そのボットを運用するダイスマスターはこの番号を確認できます。それを望まない場合は、アカウントセンターの「認可済みのボット」で認可を取り消してください。
:::

### 確認コード

認可コードはボットが個別に個人チャットで送り、通常の返信のログ、AI による加工、プラグイン、チャットのシミュレーター、保存されるセッションログを通ることはありません。確認コードを転送したり、他人の代わりに認可を完了したりしないでください。

## `.bind` コマンド

```text
.bind // 使い方をすべて表示
.bind qq <本物の QQ 番号> // QQ 公式 / Discord / KOOK の個人チャットで開始。OAuth かメールを自動で選択
.bind confirm // OAuth：Web ページで認可に同意した後、申請した同じ個人チャットで確認
.bind confirm <8 桁の確認コード> // メール：申請した同じ個人チャットで確認コードを送信。QQ の再入力は不要
.bind qq <本物の QQ 番号> email // メールでの確認を自分で選ぶ・切り替える。ダイスマスターが SMTP を有効にしている必要がある
.bind qq QQ-Official-<ボット ID>:<OpenID> // OneBot / Milky のチャットで実行し、公式のユーザーを関連付け
.bind qqgroup QQ-Official-<ボット ID>:<グループの OpenID> // 対象の OneBot / Milky のグループ内で実行。グループのオーナーか管理者の権限が必要
.bind discord <ユーザー ID> // OneBot のチャットで実行
.bind kook <ユーザー ID> // OneBot のチャットで実行
.info [qq|qqgroup] // 現在のチャットのユーザーまたはグループの識別子と、紐付け済みの接続先を表示
```

あるプラットフォームのアカウントを紐付ける前に、その人がそのプラットフォームでボットにメッセージを 1 回以上送っている必要があります。ボットは自分が見たことのある識別子しか紐付けられず、何もないところから OpenID を書き込むことはできません。

`.bind confirm` の確認方法は、サーバーに保存された申請によって決まります。OAuth の申請はメールの確認コードを受け付けず、メールの申請には確認コードの入力が必要です。旧来の書き方 `.bind email <QQ>`（メールの申請）と `.bind qq <QQ> <確認コード>`（メールでの確認）も互換のために残していますが、主な使い方としては紹介していません。

逆方向の紐付けは、メール / OAuth の手順とは別の入口です。

- 公式のユーザーは、まず公式ボットとの個人チャットで `.info qq` を使って `QQ-Official-ボットID:OpenID` を取得し、**自分の本物の QQ の OneBot / Milky のチャット** で `.bind qq <その識別子>` を実行します。
- 公式のグループは `.info qqgroup` でグループの識別子を取得し、**対象の本物の QQ グループ内** でグループのオーナーまたは管理者が `.bind qqgroup <その識別子>` を実行します。個人チャットではグループの所有を証明できません。
- Discord / KOOK のユーザーは、まずボットにメッセージを送り、そのうえで自分の本物の QQ の OneBot / Milky のチャットで `.bind discord <ユーザー ID>` または `.bind kook <ユーザー ID>` を実行します。

### 確認方法の違い

| 方法 | 使えるチャット | 証明の仕方 |
| --- | --- | --- |
| アカウントセンターの認可 | 任意のチャット（個人チャットで認可） | アカウントセンターで確認済みの、登録した QQ メールアドレス |
| OneBot のセッション | OneBot / Milky | プロトコルクライアントが確認済みの本物の QQ を直接提供 |
| グループのオーナーまたは管理者 | 対象のグループ内 | グループの識別子を紐付けるときに、実行した人の権限も確認 |
| QQ メールの確認コード | QQ 公式 / Discord / KOOK の個人チャット | 対象のQQ番号@qq.com で確認コードを受け取り、申請した同じ個人チャットで送信 |

アイコンによる確認は廃止され、ユーザーにアイコンの変更を求めることはなくなりました。メールでの確認はユーザーのアカウントにのみ使い、グループの所有の証明にはなりません。

### QQ メールの確認コード

ダイスマスターは先に「システム設定 → QQ メールによる紐付けの確認」で SMTP サーバー、ポート、アカウント、パスワードまたは認可コード、送信元のアドレスを入力し、機能を有効にしておく必要があります。これはグローバルな設定で、「通知設定」のメール通知とは別のものです。宛先のアドレスは常に対象の QQ 番号から生成され、任意のメールアドレスは受け付けません。

- 通常、465 番ポートでは暗黙の TLS を有効にし、587 番ポートではこの項目をオフにして STARTTLS を必須にします。サーバーには有効な証明書が必要で、平文での認証には対応していません。
- SMTP のパスワードは保存後に再表示されません。設定を編集するときに空欄のままにすると、元のパスワードが保持されます。
- 確認コードの有効期間は 10 分で、5 回続けて間違えると無効になります。再送すると古いコードは無効になり、ボットの再起動後は申請し直す必要があります。
- プラットフォームの身元ごと、対象の QQ ごとに 1 時間あたり最大 5 回まで送信でき、送信の間隔は 60 秒以上空ける必要があります。全体では 1 時間あたり最大 100 回です。
- 確認コードは元の個人チャットで送る必要があり、ユーザー、クライアント、対象の QQ をまたいで使うことはできません。確認コードのコマンドは、プラグイン、AI、チャットのシミュレーター、セッションの記録には入りません。
- すでに別の QQ に紐付けられているプラットフォームのアカウントは、メールの手順で紐付けを上書きできません。

メールでの確認では、クラウドのキャラクターシートのアクセストークンは与えられません。クラウドのサービスが必要な場合は、引き続き `.cloud auth` を使ってください。他人の代わりに確認コードを受け取ったり転送したりしないでください。

`.bind` の OAuth による確認も、メールアドレスの身元の権限だけを申請し、成功・失敗のどちらの場合も確認用のトークンを破棄します。`.cloud auth` によるクラウドのシートの認可とは別のものです。

## クラウドのキャラクターシート

取得したクラウドのシートは通常のローカルのシートと同じです。セッションのグループで `.pc tag <ローカルのシート名>` で紐付ければ、`.st`、`.ra`、`.sc`、シートを読む Lua / JS プラグインもいつもどおり動作します。通常のダイスロールやシートの変更ではネットワークのリクエストは一切発生しないため、ネットワークの切断、認可の解除、クラウド側の異常があっても、ローカルでのセッションには影響しません。

同期は手動で行い、バックグラウンドでの自動同期はありません。

### 競合と保護

- アップロードには実際の基準となるバージョン番号が付きます。クラウド側がほかの人に変更されている場合は競合が返され、ボットは再試行も強制的な上書きもせず、双方のデータを保持します。
- 取得によって、変更済みのローカルのシートが上書きされることはありません。`.cloud pull <クラウドのシート ID> <新しい名前>` で比較用に別のコピーを保存できます。
- ローカルで名前を変えても、同じクラウドのシートに書き戻します。自分で付けたローカルの別名が、初回の同期でクラウドのシートの名前を上書きすることはありません。
- 同じ名前の過去の重複した行、名前のないシート、未知のスキーマ、範囲外の数値ははっきりと拒否し、推測でどれか 1 つをアップロードすることはありません。

### 取り消し

`.cloud logout` は、このボットに保存された一時的な認証情報だけを消去します。認可を完全に取り消すには、アカウントセンターの「認可済みのボット」ページで取り消してください。

## ダイスマスターが行う準備

プレイヤーがクラウドのシートを使う前に、ダイスマスターはアカウントセンターでボットの所有を確認し、[クラウドサービス → ボットのキー](/ja/manage/cloud-services#ボットのキー)で現在のアダプターに正式な API キーを入力しておく必要があります。自動で申請された未確認のハートビート用の認証情報は、クラウドのシートには使えません。このキーはプレイヤーに渡さないでください。
