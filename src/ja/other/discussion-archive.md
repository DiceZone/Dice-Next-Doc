## 2026-08-11 · QQ 公式ボット 2.0 の Webhook の受信のモード（優先度は低）

### 結論

Webhook は既存の QQ 公式ボット 2.0 のアダプターと互換にでき、実装は中程度の作業量ですが、ユーザーの導入の敷居は Gateway WebSocket よりはっきり高くなります。現在の Dice!Next のユーザーの多くは公開の HTTPS のコールバックのアドレスを持っていないため、この項目は優先度の低い案としてだけ残し、近い開発の予定には入れません。既定の受信の方法は引き続き Gateway WebSocket です。

### Gateway WebSocket と Webhook の比較

| 比較の項目 | Gateway WebSocket（現在の方式） | Webhook（候補の方式） |
| --- | --- | --- |
| 公開の入口 | 不要。Dice!Next から QQ の Gateway に接続する | QQ のプラットフォームから届く公開の HTTPS のアドレスが必要 |
| 導入の難しさ | 低い。家庭のネットワーク、動的な公開 IP、内部のネットワークでも使える | 中～高。通常はドメイン、証明書、リバースプロキシ、クラウドの中継が必要 |
| 接続の維持 | クライアントがハートビート、切断後の再接続、セッションの再開を担う | 長い接続はないが、コールバックの検証、プラットフォームの再試行、リクエストのタイムアウトを扱う必要がある |
| イベントの構造 | QQ 2.0 の標準のイベント `op/t/d/id/s` | WebSocket と同じイベントの構造で、既存のイベントの振り分けを再利用できる |
| 複数のアカウント | 各アダプターが独立した Gateway のセッションを持つ | HTTP の入口は、検証したアプリの身元に従って対応するアダプターに振り分ける必要がある |
| 重複したイベント | 主に切断からの再開の間の重複した送信を扱う | プラットフォームの再試行でコマンドが重複して実行されないよう、イベント ID で重複を除く必要がある |
| 安全の重点 | Token、Gateway のセッション、接続の状態 | 元のリクエストの本文の署名の検証、時間の窓、リプレイの防止、流量の制限、本文のサイズの制限 |
| 向いている場面 | 一般のユーザー、ローカルの導入、Docker、公開の環境がない場合 | すでに公開の HTTPS のサービス、統一のゲートウェイがある、または長い接続に制限がある導入の環境 |

### 将来の実装の範囲

- QQ のアダプターの業務の処理を複製しない、独立した Webhook の HTTP の受信の層を新しく加える。
- 公式のコールバックのアドレスの検証を行い、JSON を解析する前に公式のルールで元のリクエストの本文を検証する。
- Webhook と Gateway のイベントを同じ形に整えてから、既存の `dispatch()`、身元の解決、コマンド、ログ、返信の流れに渡す。
- 複数の QQ 公式ボットのアカウントの安全な振り分けに対応し、リクエストの本文の検証していない AppID だけを信用しない。
- イベント ID ごとに有効期限付きの重複除去の記録を持つ。コールバックにはすばやく応答し、時間のかかるコマンドは非同期で処理する。
- WebUI に「Gateway WebSocket / Webhook」の受信の方法と必要な設定を加え、HTTPS、リバースプロキシ、トラブルシューティングの文書を補う。
- 1 つのアダプターでは既定で 1 つの受信の方法だけを有効にする。将来 2 つの経路での障害への備えを許す場合は、両方で重複除去の仕組みを共有する必要がある。

### 作業量の見積もり

- 最小限の使える版：約 1～2 開発日。単一のアカウントのコールバック、検証、署名の確認、既存のイベントの振り分けの再利用を含む。
- 公開テストに出せる完全な版：約 3～5 開発日。複数のアカウント、再試行の重複除去、WebUI、テスト、導入の文書を補う。
- ドメイン、証明書、内部のネットワークの公開の自動の取得はメインのプログラムに含めることをおすすめしません。こうした基盤を組み込むなら、さらに 1～2 週間と継続的な運用のコストがかかる見込みです。

### 開始の条件

明確なユーザーの需要があり、対象のユーザーが安定した公開の HTTPS のコールバックの能力を持っていること。または Dice!Next が今後、独立して持続的に保守できるクラウドのイベントの中継のサービスを提供すること。条件を満たすまでは実装を始めません。

## 2026-08-02 · プラットフォームをまたぐ身元とグループのデータの関連付け（議論の草案、未確定）

### 議論の目標

QQ 公式ボット、Discord、KOOK などのプラットフォームのアカウントが、実際の QQ を管理していることを検証した後に、既存の `QQ:<実際の QQ>` と `QQGroup:<実際のグループ番号>` の過去のデータに関連付けられるようにする。QQ / グループ番号を主キーとする古いプラグインとの互換も保つ。

### 現在の議論の方向

- ダイスマスターは元の OneBot のボットのアカウントに少なくとも 1 回ログインし、見えるグループの一覧、メンバーの QQ、オーナー/管理者の役割、取得の時刻を、過去の確認のスナップショットとして保存する。
- ユーザーが新しいプラットフォームで紐付けを始めるときは、まず関連付けたい数字の QQ 番号を申告する。OneBot がオンラインなら、その QQ に個人チャットで短時間有効な一回限りの確認コードを送る。OneBot がオフラインなら、対応する `QQ番号@qq.com` のメールアドレスに確認コードを送る。確認コードの成功は、ユーザーがその QQ の身元を管理していることだけを証明する。
- 確認を終えた後、新しいプラットフォームの「アダプター + 元のユーザー ID」を別名として `QQ:<実際の QQ>` に関連付け、統一の身元の解決で元の個人のデータを読む。古い記録をコピー、連結、上書きすることはしない。
- 確認済みの過去のグループのオーナーは、新しいプラットフォームのグループを過去の `QQGroup:<実際のグループ番号>` に関連付けられる。システムはまず、その QQ が OneBot の過去のスナップショットでグループのオーナーであることを確認し、一回限りのグループの紐付けのコードを作り、対象のプラットフォームの対象のグループで確認を完了するよう求める。OneBot がオンラインなら先に役割のスナップショットを更新すべきで、オフラインなら時刻の印の付いた過去の確認の結果だけを使える。
- グループの関連付けで引き継ぐのは、キャラクターシート、セッション、ログの関連付け、ルール/業務の設定などのデータの入口だけで、キック、グループの退出、管理者の一覧、古いグループの管理の権限は **引き継がない**。新しいプラットフォームの管理の操作は常に、新しいプラットフォームで読める現在の役割に従う。QQ 公式ボットに役割の API がない場合、グループの管理の権限は補わない。
- OneBot がまったくない場面でも、仮想の QQ / グループの主キーと両側の一回限りの確認コードで論理的な関連付けを作れるが、その論理的なグループが実際の QQ のグループとして確認済みだとは言えない。

### まだ決まっていないこと

- QQ のメールの確認コードの送信のサービス、頻度の制限、失敗の案内、QQ のメールが有効化済みであることを求めるか。
- 対象のプラットフォームでグループの役割を読めない場合、確認済みの過去のグループのオーナーがそのままデータの関連付けを完了してよいか、それともダイスマスターが WebUI で追加の確認をする必要があるか。
- 両側にすでに個人/グループのデータがある場合の衝突の扱いと、元に戻せる統合の流れ。
- 過去のグループのオーナーのスナップショットの有効期限、更新の頻度、権限が変わった後の扱い。
