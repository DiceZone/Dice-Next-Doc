# MCP サービス

**管理パネル → システム設定 → MCP サービス**。外部の AI クライアントから Dice!Next の機能を呼び出せるようにするサーバーで、ボット自身の AI の会話やツール呼び出しの設定とは独立しています。

::: info 開発版の機能
このページでは MCP サーバーの最初の版について説明します。使う前に、メインのプログラムと WebUI の両方にこの機能が含まれていることを確認してください。古い WebUI やメインのプログラムをインストールしても、この API が自動で使えるようにはなりません。
:::

## できること

| ツール | 機能 | 制限 |
| --- | --- | --- |
| `roll_dice` | 実際の Dice!Next の数式パーサーでダイスを振り、結果、各ダイスの出目、過程を返す | `d100`、`2d6+3` など。OneDice／DiceScript のスクリプト、プラグイン、テンプレートは実行しない |
| `search_help` | 読み込み済みのヘルプ文書を検索 | 原文を最大 20 件返し、長い本文は切り詰める。文書内の変数やコードは実行しない |
| `get_status` | バージョンと稼働時間を照会 | キー、アカウント、接続先のアドレス、設定全体は返さない |
| `get_character_card` | 明示的に認可したキャラクターシートを読む | シートの番号ごとに認可し、読み取りロックに従い、式を評価したり紐付けを変えたりはしない |

最初の版では、メッセージの送信、キャラクターシートの変更、任意のコマンド／プラグインの実行、設定の変更、プログラムの再起動や更新のツールは **提供しません**。ヘルプやキャラクターシートの中の文章はデータであり、AI が新たな操作の認可として扱うべきものではありません。

## 認可の作成

1. ダイスマスターとしてパネルにログインし、**MCP サービス** を開きます。権限が制限された管理者は、このページの認可を読んだり変更したりできません。
2. **認証情報を作成** をクリックし、アプリ／使う人のラベルを入力して、許可するツールと有効期間（1–365 日、既定は 30 日）を選びます。
3. キャラクターシートを読む必要がある場合は、シートの名前や所有者のユーザー ID で検索し、具体的なシートを明示的にチェックします。空欄のままで「すべてのキャラクターシート」の権限が得られることはありません。
4. 作成したら認証情報を AI クライアントに保存します。**平文は 1 回だけ表示され**、ブラウザには保存されず、サーバーは SHA-256 のダイジェストだけを永続化します。紛失した場合は生成し直すか、取り消して作り直してください。
5. **MCP サービスを有効にする** をオンにして保存します。認証情報を作成しただけではサービスはオンになりません。

ツール／シートの範囲の変更、無効化、取り消し、期限切れの確認は、リクエストのたびに改めて行い、クライアントが自分から接続を切るかどうかには頼りません。

- **認可の編集** では、既定で元の有効期限を保持します。「有効期間を計算し直す」をオンにしたときだけ、保存した時点から入力した日数で延長し、期限切れの認証情報をこっそり復活させることはありません。
- クライアントの項目の **その他の操作 → 認証情報を生成し直す** で、その場で入れ替えられます。古い認証情報はすぐに無効になり、新しい平文は 1 回だけ表示されます。ツール／シートの範囲、有効の状態、有効期限は変わりません。AI クライアントの設定を忘れずに更新してください。
- シートが削除されたり読み取りロックされたりした後も、認証情報の無効化、シートの読み取り権限の削除、認可の取り消しができます。シートの所有者が変わっても認可は自動で引き継がれません。まずそのシートの認可を削除して保存し、改めて明示的に選び直してください。

MCP 専用の認証情報は、WebUI の Cookie、BDC のキー、管理用の API キーの代わりにはなりません。逆に、それらの認証情報で MCP にログインすることもできません。

認可の一覧は **サーバーの時刻** で有効期限の状態を表示し、ページを開いているあいだは定期的に更新し、7 日以内に期限が切れる項目を知らせます。ブラウザのコンピューターの時計のずれの影響は受けません。自動で延長することも、期限切れの通知を別途送ることもありません。

「保持されている最近の成功した呼び出し」は、現在保持している 5,000 件の監査記録のうち、成功したツールの呼び出しだけを数え、初期化、セルフチェック、認可の変更は含みません。記録がないことは一度も使われていないことを意味しません。監査の保存領域を読めない場合ははっきりと知らせ、「一度も使われていない」ように見せかけることはありません。

シートの読み取りの認可を編集するときは、選択したシートの名前、所有者、現在の読み取りの状態を表示します。削除と読み取りロックはどちらも「キャラクターシートが存在しないか、読み取りがロックされています」と表示し、具体的な理由を推測しません。所有者が変わった場合は認可し直すよう知らせます。ここではシートの概要だけを照会し、能力値の内容は返しません。

### 保存、タイムアウト、復旧

ページの読み込みの待ち時間の上限は 10 秒、変更の操作は 20 秒です。ネットワークの切断やタイムアウトは **変更が失敗したことを意味しません**。ページはそれ以上の変更をいったん止め、「操作の状態を確認」を表示し、認証情報の作成や入れ替えを自動で繰り返すことはありません。

状態を確認した後は、サーバーの設定と認証情報の一覧も読み直します。読み直しに失敗した場合は操作のロックと元の編集内容を残し、古い一覧を最新の状態として見せることはありません。後でもう一度確認できます。

- まだ処理中：しばらくしてからもう一度確認し、重ねて送信しないでください。
- 保存されたが 1 回限りの認証情報を受け取れなかった：一覧で該当する項目を探して確認し、手動で「認証情報を生成し直す」を行ってください。失われた平文を読み直すことはできません。
- 反映されなかった：確認した後にもう一度送信できます。
- 状態が不明：プログラムが再起動したか、一時的な状態の記録が消去された可能性があります。まず現在の設定と認証情報を確認し、「不明」を失敗とは見なさないでください。状態の記録は一時的に最大 128 件だけ保持し、認証情報の平文は保存しません。

設定は単一のファイルとしてアトミックに保存します。「変更は反映されましたが、呼び出しの記録を保存できませんでした」と表示された場合、権限の変更は反映済みで、新しい認証情報も通常どおり保存できます。`data/audit` の書き込み権限と空き容量を確認し、直前の操作を繰り返さないでください。

### バックアップからの復元後

設定やメインのデータベースを復元すると、**MCP の全体スイッチと古い認可は無効になり、古いキーも使えなくなります**。バックアップによって、すでに取り消したキーが戻ってくるのを防ぐためです。認可の名前、ツール、キャラクターシートの範囲は、ダイスマスターが確認できるよう残ります。

1. MCP サービスを開き、残っている認可の範囲を確認します。
2. 引き続き使う項目では「認証情報を生成し直す」を選び、新しい平文を安全に保存して AI クライアントを更新します。
3. 必要な認可を明示的に有効にします。期限切れのものは有効期間の再計算も必要です。
4. MCP の全体スイッチをオンにして保存します。全体スイッチをオンにし直したり認可を編集したりするだけでは、古いキーが再び有効になることはありません。

デッキ、画像、プラグインなどのリソースだけを復元し、設定やメインのデータベースを上書きしない場合は、MCP の認可はリセットされません。Windows でもほかのプラットフォームでも、コアが起動時に復元を一括で適用します。設定やデータベースのスナップショットの書き込みに失敗した場合は起動を中止し、復元の保護の目印を残します。保存領域を直してから再試行してください。保護を回避するために目印を手動で削除しないでください。

## クライアントの接続

サービスは **Streamable HTTP** を使い、API のパスは `/mcp` です。同じサーバーのクライアントはページに表示された `http://127.0.0.1:ポート/mcp` を使えます。リモートのクライアントはアクセスできる HTTPS のアドレスを使ってください。リバースプロキシにパスの接頭辞がある場合は、その接頭辞を残してください。

以下は汎用の接続パラメーターで、すべてのクライアントで共通の設定ファイルの形式ではありません。クライアントの要求に従って URL、通信方式、リクエストヘッダーを入力してください。

```json
{
  "transport": "streamable-http",
  "url": "http://127.0.0.1:18088/mcp",
  "headers": {
    "Authorization": "Bearer <MCP_TOKEN>"
  }
}
```

ボットのマシンに Node／Python を追加でインストールする必要はなく、このページにモデルの API キーを入力する必要もありません。呼び出す側は HTTP の MCP とカスタムの Bearer の認証情報に対応している必要があります。ローカルの stdio にしか対応していないクライアントは、この入口に直接接続できません。最初の版では自動の OAuth ログインは提供していません。

セッションなしの `2026-07-28` のプロトコルと、`2025-11-25`、`2025-06-18` の初期化の互換に対応しています。旧来の HTTP+SSE のエンドポイントや stdio での起動方法は提供していません。プロトコルのメッセージとリクエストヘッダーは MCP クライアントが組み立てるため、ユーザーが手で書く必要はありません。

## ローカルとリモートからのアクセス

### ローカルの接続のセルフチェック

接続の案内には **ローカルの接続のセルフチェック** があります。認証情報を入力しない場合は、保存済みのサービスのスイッチ、監査の保存領域に書き込めるか、使える認証情報があるかを確認します。既存の MCP の認証情報を入力すると、さらにローカルのプロトコルの処理の初期化とツールの一覧を確認し、特定のツールの使用が許可されているかも確認できます。

セルフチェックでは一時的な認可を作らず、ツールを実行せず、任意の URL にも接続しません。入力した認証情報は今回の確認にだけ使い、終わると消去し、ブラウザに保存したり、ログに記録したり、結果に表示したりはしません。無効、無効化済み、取り消し済み、期限切れの認証情報は、いずれも「認証情報が拒否されました」と表示します。頻度制限やパネルのリクエストの失敗を、認証情報の無効として誤って報告することはありません。

::: warning セルフチェックに通ってもインターネットから使えるとは限りません
セルフチェックではローカルのプロトコルの処理だけを確認し、待ち受けポートへの到達性、インターネットの DNS、TLS 証明書、リバースプロキシ、ブラウザのオリジンは確認しません。実際の AI クライアントで本当のアドレスをテストする必要があり、セルフチェックの合格でリモートの接続の確認を代えることはできません。
:::

### アクセスの範囲の設定

既定ではリモートからのアクセスはオフで、ループバックの接続だけを受け付け、プロキシの転送情報を含むリクエストは拒否し、`Host` も確認します。これはリクエストごとの制限で、WebUI の既存の待ち受けアドレスを変えるものではありません。

- リモートからのアクセスは自分で有効にする必要があり、`dice.example.com` や `dice.example.com:8443` のような正確な Host の許可リストを設定します。`*` は使わず、プロトコルやパスも含めません。
- インターネットの入口では HTTPS を使ってください。リモートからの平文のリクエストは直接拒否します。ローカルのリバースプロキシで TLS を終端する場合、インターネットの入口が HTTPS だけを提供し、バックエンドの平文のポートへのアクセスを制限することを、ダイスマスターが保証する必要があります。偽造された `X-Forwarded-Proto` によってリモートの平文の接続を信頼することはありません。
- ローカルのリバースプロキシでは、接続がループバックのアドレスから来ていても、プロキシ側で `/mcp` を明示的に制限してください。「ローカルモード」をインターネットからのアクセス制御の代わりとして扱わないでください。
- ネイティブのクライアントは通常 `Origin` を送りません。ブラウザのクライアントでオリジンをまたいだアクセスが必要な場合は、`https://ai.example.com` のような正確なオリジンを別途設定する必要があります。既定ではどのブラウザのオリジンも許可せず、`null` やワイルドカードも受け付けず、Cookie を MCP の認証に使うこともありません。

ホスト名は大文字・小文字を区別しません。ブラウザのオリジンは大文字・小文字をそろえ、HTTP／HTTPS の既定のポート（80／443）を統合します。これによってサブドメインや既定以外のポートの制限が緩むことはなく、たとえば `https://ai.example.com:8443` は引き続き個別に認可する必要があります。

管理ページのクロスサイトの防御と、MCP クライアントのオリジンの許可リストは独立しています。AI の Web ページに `/mcp` へのアクセスを認可しても、ボットの MCP の設定の変更を認可したことにはなりません。リバースプロキシではブラウザの `Origin`、`Sec-Fetch-Site`、`X-Dice-MCP-Request` のリクエストヘッダーを残し、`/api/system/mcp` へのオリジンをまたいだ書き込みを開放しないでください。ネイティブの管理用の API キーでの呼び出しでは、引き続き JSON のリクエストを使えます。

## 呼び出しの記録と制限

ページにはサーバー側でページ分けした呼び出しの記録があり、最新の **5,000 件** を永続的に保持します。クライアントと成功／拒否／失敗の結果を組み合わせて絞り込め、件数とページ分けは絞り込んだ結果で計算します。記録のクライアント名をクリックするとそのクライアントの履歴を確認でき、取り消したクライアントの記録も引き続き絞り込めます。認可したクライアント、操作、時刻、結果を記録し、**認証情報、リクエストのパラメーター、キャラクターシートの内容は保存しません**。

認証情報ごとに 1 分あたり最大 60 リクエストで、ほかに接続元ごとの頻度制限もあります。1 回のリクエストは最大 32 KiB、結果は最大 64 KiB です。数式は最大 256 バイト、括弧は 16 段、ランダムな出目は 1,000 個、1 つのダイスの面は最大 1,000,000 面で、整数のオーバーフローは計算を続けずにエラーを返します。ヘルプの検索は 1 回あたり最大 10,000 件／4 MiB の本文を調べ、上限に達すると明示的に `search_truncated` を返します。照会の失敗、取り消し、権限の超過の場合に、代わりにほかのツールを実行することはありません。

ツールと管理のリクエストは独立したバックグラウンドの作業キューを使い、待ち行列にはいずれも上限があります。混雑している場合や 5 秒を超えて待った場合は `503` を返し、それ以上たまって Web サーバーのスレッドを止めることはありません。認証情報ごとに、待機中または実行中のツールの呼び出しは同時に 1 つだけで、ほかの同時の呼び出しはツールを実行せずに `429` を返します。前の呼び出しが終わってから再試行できます。接続の初期化とツールの一覧の照会はこの枠を使いません。

ツールの実行には 5 秒の協調的な取り消しの期限もあり、プログラムの終了時にも照会に取り消しを通知します。期限切れや取り消しの後は照会の結果を返しません。C++ のスレッドを強制終了することはなく、下の層ですぐに中断できないシステム／データベースの呼び出しは、戻ってきてから取り消しの状態を確認します。照会が終わった後に認可を再確認し、そのあいだに取り消し／無効化された、または範囲が狭められた結果をクライアントに返すことはありません。

呼び出しの記録は `data/audit/mcp.db` に保存されます。バックアップで「監査記録」を選ぶと、SQLite のスナップショットで現在の記録を含めるため、サービスを止める必要はありません。

よくあるエラー：`401` は専用の認証情報、有効期間、有効の状態を確認します。`403` はアクセス元、Host／Origin、ツール／シートの認可を確認します。`429` は少し待ってから再試行します。`503` は混雑の状態と監査の保存領域を確認し、管理の変更では先に操作の状態を確認します。`404` は MCP の全体スイッチ、API のアドレス、クライアントが対応しているプロトコル／メソッドを確認します。
