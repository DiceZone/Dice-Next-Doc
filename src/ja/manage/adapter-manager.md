# アダプター管理

**管理パネル → プラットフォームの接続** で、接続の追加、オン・オフ、監視を行います。接続の状態は数秒ごとに自動で更新され、ページを手動で再読み込みする必要はありません。

## アダプターの追加

QQ 公式ボットを追加した後は、**高度な返信 → カードとボタン**、またはアカウントのカードの「その他 → カードとボタン」のショートカットから、アカウントごとに 1 対 1 チャットのメニューとコマンドパネルを視覚的に編集できます。具体的な場面、項目の制限、関連する操作については [QQ 公式 API v2](/ja/develop/qq-official-api#視覚的な編集) を参照してください。

「接続を追加」をクリックすると、フォームは **段階的な案内** になっています。まず接続方式を選ぶと、アドレスなどの後続の項目が表示されます。

OneBot v11、Milky、QQ 公式ボット、Discord、KOOK、実験的な OpenOPQ の内蔵ログインに対応しています。まずプラットフォームを選び、そのプラットフォームに合わせて認証情報とエンドポイントを入力します。下の表の接続方式の説明は OneBot v11 向けです。Milky と内蔵ログインは下の専用の節を参照し、ほかのプラットフォームはそれぞれの接続の項目を使います。

| 項目 | 説明 |
|------|------|
| アダプター名 | 識別用の表示名 |
| アダプターの種類 | 実際のプラットフォームに合わせて選ぶ。この表は OneBot v11 の例 |
| 接続方式 | 正方向 WebSocket / 逆方向 WebSocket |
| 接続アドレス / ポート | 正方向はエンドポイントのアドレス（例：`ws://127.0.0.1:3001`）、逆方向はこのプログラムが待ち受けるポート |
| Access Token | 認証トークン（任意）。空欄なら検証しない |

- 接続方式の横には **? のヘルプアイコン** があり、マウスを合わせると正方向 / 逆方向の詳しい説明を表示します。選んだ後もフォーム内に対応する案内が表示されます。
- 正方向のアドレスはスキームを **自動で修正** し（書き忘れた場合は `ws://` を補い、`http/https` は `ws/wss` に変換）、不正なアドレスやポートはすぐに注意が表示されます。

### 通信方式の説明

| 方式 | 動作 | フレームワーク側の設定 |
|------|------|------|
| 正方向 WebSocket（`forward_ws`） | このボットが WS クライアントとして、ログインフレームワークの OneBot v11 の WS サーバーに **接続しに行く** | 「WebSocket サーバー / 能動的な WebSocket / 正方向 WebSocket」を選び、フレームワークの待ち受けポートを入力 |
| 逆方向 WebSocket（`reverse_ws`） | このボットが WS サーバーとしてローカルのポートで待ち受け、**フレームワークからの接続を待つ** | 「逆方向 WebSocket / 受動的な WebSocket / WebSocket クライアント」を選び、`ws://このマシンのIP:ポート` を入力 |

::: tip 正方向と逆方向の区別
「どちらから接続を始めるか」で区別します。正方向＝Dice!Next がフレームワークに接続しに行く、逆方向＝フレームワークが Dice!Next に接続してくる、です。両側の設定を 1 対 1 で対応させる必要があります。
:::

逆方向 WS のアダプターでは、「接続方式」をクリックすると **接続情報** を確認できます。アドレスは Dice!Next を動かしているサーバーのもので、パネルを開いているコンピューターのものではありません。

- **ローカル**：`127.0.0.1`。フレームワークとボットが同じサーバーで動いている場合にだけ使えます。
- **LAN**：サーバーの有効な IPv4 のネットワークアダプターから読み取ります。複数のアダプター、VPN、コンテナの環境ではアドレスを選べます。
- **インターネット**：バックエンドが外部のサービスを通じてサーバーの送信元の IPv4 アドレスを調べ、LAN の IP を使い回すことはしません。

プログラムの起動後にバックグラウンドで事前に検出し、15 分ごとにキャッシュを更新します。ダイアログを開いたときはキャッシュを読むだけで、インターネットの検出をやり直すことはありません。「アドレスを更新」で手動で検出できます。読み取りの失敗、検出の失敗、検出中はそれぞれ別に表示し、更新に失敗した場合は表示中の古いアドレスであることをはっきり示します。アドレスがない場合、仮の文字をコピーすることはできません。

インターネットの照会には固定の HTTPS のアドレスのサービスを使います：[ipify](https://www.ipify.org/) と [AWS checkip](https://docs.aws.amazon.com/batch/latest/userguide/create-a-base-security-group.html)。サーバーの送信元の IPv4 を知るためだけに使い、設定、アカウント、キーをアップロードすることはありません。システムの `curl` が使えない、ネットワークにつながらない、照会がタイムアウトした場合は取得できなかったことを表示し、プログラムの起動やメッセージの送受信を妨げません。

::: warning インターネットの IP があってもポートに届くとは限りません
インターネットからの接続には、NAT／コンテナのポートの割り当て、サーバーのファイアウォール、セキュリティグループの確認が引き続き必要です。アドレスの検出で自動的にポートを開けたり、これらの設定を変えたりすることはありません。LAN に IPv4 がない場合や外部の照会が使えない場合も、正しいアドレスを手動で使うことには影響しません。
:::

## QQ 公式ボット

イベントの受信方式として **WebSocket** または **Webhook** を選びます。カードには実際の接続方式がそのまま表示され、「接続方式」をクリックすると接続の説明を確認できます。

- ログインの欄は四角い QR コードで、下の「AppID と AppSecret を手動で入力」をクリックすると認証情報のフォームに切り替わります。既存のアカウントを編集するときは認証情報をそのまま表示し、AppSecret を空欄にすると元の値を保持します。ボットの本当の QQ 番号は公式 API から取得するため、手動で入力する必要はありません。
- Webhook を選ぶと、フォームは現在のパネルにアクセスしているドメインとデプロイ先のパスからコールバックアドレスを生成します。追加に成功した後も接続情報が開き、アドレスをコピーして QQ オープンプラットフォームに貼り付けられます。例：パネルのアドレスが `https://dice.example/bot/#/adapters` の場合、コールバックアドレスは `https://dice.example/bot/qq-official/webhook` です。リバースプロキシではこのパスをボットのサービスへ転送する必要があり、QQ がインターネットからアクセスできなければなりません。ローカルのアドレスはローカルでの確認用です。1 つの AppID には Webhook のアダプターを 1 つだけ設定してください。
- `127.*`、`localhost`、IP アドレス、または HTTP でパネルにアクセスしている場合は、Webhook のデプロイの要件を表示します。コールバックのサーバーにはインターネットの IP が必要で、ドメインには有効な TLS 証明書を設定し、インターネットからアクセスできる HTTPS のアドレスでイベントを受け取る必要があります。リバースプロキシを設定している場合は、その HTTPS のドメインからパネルを開いてからアドレスをコピーしてください。これらの条件を満たせない場合は WebSocket を選んでください。この案内は保存を妨げず、パネルがインターネットからの到達性を確認したことも意味しません。
- WebSocket ではボットから QQ に接続しに行くため、コールバックアドレスの設定は不要です。画面の WebSocket は設定ファイルの `receiveMode: gateway` に対応し、旧来の設定も互換のまま使えます。
- QQ 公式 API v2 の一部の API（グループメンバーの一覧など）は、招待や許可リストに入ったアプリにだけ公開されています。一般のアプリが呼び出すと、プラットフォームは「アプリに API のアクセス権限がありません」（エラーコード 40012010）などの権限のないエラーを返します。これはプラットフォームの権限によるもので、不具合ではありません。プログラムのログには DEBUG として記録してログを埋めないようにし、ニックネームなどの関連する機能は使える API に合わせて機能を落とします。既定の INFO レベルではこれらの記録は見えないので、調査するときは WebUI 設定で一時的にログのレベルを下げてください。
- 「高度なオプション」には、Markdown の画像リソースの厳密な検証、グループメンバーの参加・退出イベントの購読、インタラクションイベントへの自動応答、リッチな返信のスタイル、ショートカットの操作がまとめられています。**新規作成** では既定で Markdown とメッセージのボタンが使われ、グループメンバーのイベントの購読とインタラクションイベントへの自動応答もオンになります。既存のアカウントを編集する場合は元の設定を保持します。画像リソースの厳密な検証は既定でオフです。

## Milky の接続

API には HTTP / HTTPS のベースアドレスを入力し、イベントには WebSocket を使います。イベントのアドレスは個別に設定でき、空欄の場合は API のベースアドレスから `/event` を導きます。現在 Webhook には対応していません。OneBot のエンドポイントをそのまま Milky のアドレスとして使わないでください。詳しくは [Milky の設定](/ja/config/adapter#milky-アダプター)を参照してください。

## 内蔵ログイン（OpenOPQ、実験的）

「接続を追加」で「内蔵ログイン」を選び、QQ 番号と有効な **BDC のボットの API キー** を入力します。保存して有効にすると、Dice!Next はセンターから対応するシステム向けのプロトコルクライアントをダウンロードしてこのマシンで起動し、ログインのダイアログにダウンロードの進捗、QR コード、オンラインの状態、または失敗の理由を表示します。2 つの WebUI のどちらでも使えます。

- 既定は正方向 WebSocket で、ポートと接続の認証情報はプログラムが割り当てるため、リモートのアドレスを入力する必要はありません。逆方向モードは、プロトコルクライアントが対応している場合にだけ選んでください。
- 実行ファイルは Dice!Next のインストールパッケージには同梱されていません。ダウンロードはマニフェストの署名、サイズ、SHA-256 の検証を通る必要があり、センターが現在のシステム向けのバージョンを提供している必要があります。有効なキーがない場合、ネットワークに届かない場合、センターがまだそのプラットフォームを提供していない場合はエラーを表示し、検証を飛ばすことはありません。
- 現在のプロトコルクライアントは再起動後に再びスキャンが必要です。ログインのウィンドウでは QR コードの更新、スキャンの取り消し、QQ の切断ができます。「接続をテスト」は既存のインスタンスを確認するだけで、2 つ目のプロトコルクライアントを起動することはありません。
- アカウントのデバイスのデータとログは `data/openopq/<アダプター ID>/` に、実行ファイルは `runtime/openopq/<バージョン>/` に保存されます。アダプターを削除すると、そのアカウントのローカルのデバイスのデータとログも削除されます。
- センターがキーを拒否した場合（401 / 403）は自動の再試行を止めます。キーを変更するか手動で再接続してから、もう一度試してください。通常の OneBot のアダプターはこの管理の仕組みの影響を受けません。

これは実験的な第三者のプロトコルによるログインで、QQ 公式ボットの API ではなく、プラットフォームへのログインの成功や長期的な安定性は保証されません。ボットの API キーとローカルのアカウントのデータは大切に保管してください。

## ボットのクラウドサービスのキー

アダプターのボットの API キーの入口は残っており、[クラウドサービス → ボットのキー](/ja/manage/cloud-services#ボットのキー)と同じ設定を読み書きします。これはプラットフォームの Access Token ではありません。入口が移ったことで既存のキーを入力し直す必要はありません。

## 編集 / テスト / 削除

- **編集**：変更して保存すると、アダプターは新しい設定で再接続します。**アダプターのプラットフォームの種類は作成後に変更できません**（プラットフォームを変える場合は削除して作り直してください）。
- **テスト**：エンドポイントに到達できるかを確認します。
- **再接続**：手動ですぐに再接続します。
- **削除**：そのアダプターを削除します。

## 切断後の再接続と待ち時間の延長

接続が切れると、待ち時間を延ばしながら自動で再接続します。最初の 10 回は 5 秒ごと → 11〜20 回目は 60 秒ごと → 20 回を超えると一時停止し、「**接続タイムアウト**」の状態を表示します（「無効」とは区別されます）。このとき「有効にする」をクリックすると、手動で再接続を再開できます。接続が 30 秒以上続いたときだけ再試行の回数をリセットするため、「一瞬つながってすぐ切れる」ことで際限なく素早く再接続を繰り返すことはありません。

接続に異常があるときは、[動作の概要](/ja/manage/dashboard)の最近のログで、接続や送受信の詳しい情報を確認できます。
