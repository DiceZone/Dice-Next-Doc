# 通知設定

**管理パネル → システム設定 → 通知設定** で、受け取るウィンドウごとに、通知の出所、購読の範囲、監査ログを管理します。

## 通知ウィンドウ

ページはカード／一覧の表示、検索、サーバー側でのページ分けに対応しています。カードには受け取る相手のニックネーム、アカウント、アイコンを表示し、編集をクリックすると購読するイベントを調整できます。

上部の追加ボタンをクリックし、まず **1 つの通知ウィンドウ** を選びます：1 つのグループ、1 人のユーザー、1 つの受信用メールアドレス、または 1 つの Webhook です。チャットのウィンドウでは、次に送信に使うアカウントを選び、同じプラットフォームの複数のアカウントを選べます。メールと Webhook もそれぞれ独立したウィンドウとして管理します。同じ相手を重ねて追加することはできないので、既存のウィンドウを編集してください。

続いて、このウィンドウが受け取る出所（すべてのアダプター、1 つまたは複数のプラットフォーム、1 つまたは複数のボットのアカウント）と購読の範囲（すべての通知、レベルごと、具体的なイベントごと）を設定します。システムの更新など、具体的な出所のアカウントがないイベントは、「プログラム全体の通知も受け取る」で個別に制御します。ダイアログは上部で保存し、内容の欄は独立してスクロールし、広い画面では 2 列、狭い画面では 1 列になります。

以前から同じウィンドウを指していた複数のルールは、まとめて表示されますが、各ルールの出所とイベントの範囲は引き続き個別に保存され、購読が広がることはありません。たとえば「アカウント A の友だちの通知」と「アカウント B のエラーの通知」が、「A と B のすべての友だちとエラーの通知」にまとめられることはありません。旧ルールが異なる送信用のアカウントを使っている場合は既定でそのまま残し、送信用のアカウントを 1 つにそろえると明示的に選んだときだけ変わります。

出所の絞り込みと送信用のアカウントの選択は独立しています。明示的に指定した送信用のアカウントが、失敗したときに勝手に別のアカウントに切り替わることはありません。自動選択のモードのときだけ、既存の方針に従って同じプラットフォームの使えるアカウントを試します。

チャットで `.notice on`（ダイスマスターのみ）を送って、現在のチャットを通知ウィンドウにすることもできます。詳しくは[管理コマンド](/ja/use/admin)を参照してください。

各ウィンドウでは、受け取る通知のイベントを **1 つずつ選択** できます。イベントは 4 つの区分に分かれています。

| 区分 | レベルの値 | 含まれるイベント |
|------|--------|----------|
| 日常の通知 | 1 | 信頼、アカウントの権限の関連付け、定期タスク、通知の購読の変更 |
| 重要な通知 | 2 | 友だちとグループの申請、ボットのグループへの参加・退出、ミュートとグループ管理者の権限、各種の自発的な退出のルール、グループのオン・オフ、タスクの実行、全体のサイレント、更新の進捗。禁止語の実際のレベルはルールによって変わる |
| 重大な通知 | 4 | ボットの管理権限、ブラックリスト・ホワイトリスト、ボットの一覧の変更 |
| エラーの通知 | 8 | 実行時のエラー、退出のリクエストの失敗、更新の失敗 |

`.notice level <n>` のコマンドで購読した場合（1 日常 / 2 重要 / 4 重大 / 8 エラー。足し合わせ可能、15 = すべて）、既定で対応する区分のすべてのイベントが選択されます。

これはプログラムのログの TRACE／DEBUG／INFO／SUCCESS／WARN／ERROR の絞り込みとは別のものです。旧版から取り込んだ空のイベントの一覧はレベルでの購読の意味を保ち、実際に有効なイベントで表示します。明示的にイベントごとの購読に切り替えて一覧を空にした場合だけ、イベントを受け取らないことになります。

更新の確認はシステムのイベントで、具体的な出所のグループはありません。自動インストールの結果はマネージャーが再起動した後に報告し、実際に動いているバージョンと照合します。レベルでの購読には、新しく追加された同じレベルのイベントも含まれます。すでに 1 つずつ絞り込んだルールが勝手に広がることはないので、必要に応じて新しいイベントを選択してください。

## 通知での結果の表し方

```text
[骰娘被踢出群聊] 骰娘被小明(3569827618)踢出群未归星璇(792364383)。
适配器 OneBot:3626455591
```

（「[ボットがグループからキックされました] ボットは 小明(3569827618) によって 未归星璇(792364383) からキックされました。アダプター OneBot:3626455591」）

自発的な退出は、「リクエストを送信済みで、プラットフォームの確認待ち」と、プラットフォームの実際の通知に分けて扱います。ほかの人を名指ししたキックの通知と、解散の通知は、それ以前の自発的なリクエストより優先されます。ほかの操作者のいない「キック」の通知（操作者が空、0、またはボット自身）は、このプログラムが直前に送った退出のリクエストと一致すれば自発的な退出として確認し、ブラックリストやクラウドブラックリストには書き込みません。

キック・ミュート時の自動ブラックリスト登録は[システム設定 → 元祖のグローバル設定 → イベントへの反応](/ja/manage/settings#元祖のグローバル設定)で設定し、新規インストールでは既定でオフです。ほかの人を名指ししたキックのときだけ操作者をブラックリストに登録し、上で説明した退出の通知では登録しません。理由がわからない場合はわからないとはっきり書き、操作者のアカウントだけで推測することはありません。

友だちとグループ参加の申請では、申請者、グループ、処理の判断とその根拠を書きます。承認の呼び出しでは「自動の承認／拒否を送信しました」とだけ示し、関係が成立したかは実際のプラットフォームのイベントで確認します。

名前は、まずイベントと出所のアカウントのキャッシュを使い、次に過去の記録を調べます。信頼できる名前がなければアカウントのままにし、ニックネームを作り上げることはしません。パネルのパスワードでのログインで確認できる QQ の身元がない場合は、そのとおりに注記します。プラグインのエラーでは、プラグイン名、操作、実際のインタープリターのエラー（実際の行番号を含む）を残し、下の層が報告していない根本原因を推測することはありません。

## メールと Webhook のウィンドウ

QQ にいなくても通知を受け取れます。

### SMTP メールでの送信

権限／本人確認のページの共有の SMTP の設定を優先して使うため、ウィンドウでは受信用のメールアドレスを 1 つ入力するだけで、SMTP のパスワードを重ねて入力する必要はありません。共有の送信設定がない場合は、旧来の通知用の SMTP を互換のために使います。465 では SSL を使い、587 などはメールの送信設定に従います。

有効な SMTP の設定がない場合、エディターに案内を表示して保存を止めます。「SMTP を設定」をクリックすると、既存の設定を新しいタブで開けます。戻ってくると設定の状態を更新し、元のウィンドウの下書きは残ります。受信用のウィンドウを編集・削除しても、旧来の通知用の SMTP の認証情報が消えることはありません。

メールの件名は `[Dice!Next] イベントのタイトル` で、本文はチャットの通知と同じです。変更の通知で認可コードなどの情報を漏らすことはありません。

### Webhook での送信

ウィンドウを追加するときに Webhook を選び、完全な HTTP(S) のアドレスを入力します。アドレスが未入力または無効な場合は注意を表示し、アドレスの入力欄へ移動するボタンを用意します。

汎用の JSON、WeCom（企業微信）、DingTalk（钉钉）、Feishu（飛書）のプリセットが組み込まれています。対応する種類を選ぶと、テキストメッセージのリクエストボディを生成します。DingTalk や Feishu のボットで署名を有効にしている場合は、高度なオプションで署名の秘密鍵を入力すると、送信時にタイムスタンプと署名を生成します。ボット自身のキーワードや IP の許可リストなどの制限は、引き続きサービス提供者の要求に従って設定する必要があります。汎用の JSON は既定で `POST` を使い、形式は互換を保っています。

```json
{ "ts": "…", "level": 2, "op": "group_left", "title": "骰娘被踢出群聊", "msg": "[骰娘被踢出群聊] …", "origin": "onebot_v11:792364383" }
```

`op` は安定した購読のキーで、`title` は具体的な結果に応じてキック、自発的な退出、解散を区別します。メールと Webhook も同様にルールのレベル／イベントと出所の絞り込みで制御され、旧来のグローバルな経路とも互換です。

### 高度なリクエストと通知の変数

高度なオプションでは、`POST`／`PUT`／`PATCH`、固定の JSON のリクエストヘッダー、カスタムの JSON のリクエストボディに対応しています。「リクエストボディの例」はブラウザ内でプレビューするだけで、ネットワークのリクエストは送りません。プリセットを切り替えると、その種類のテンプレートに戻ります。

変数は JSON の文字列の値の中に書きます。プレースホルダーだけの値は変数の型を保ち、たとえば `"severity": "{{level}}"` は送信時に数値になります。通知の本文の引用符や改行は自動で JSON のエスケープを行うため、本文全体を手動でエスケープしないでください。

```json
{
  "summary": "{{title}}",
  "text": "{{message}}",
  "severity": "{{level}}",
  "source": { "adapter": "{{adapter_id}}", "group": "{{group_name}}" }
}
```

| 変数 | 内容 |
| --- | --- |
| `{{message}}` | 通知の本文全体 |
| `{{title}}` | このイベントのタイトル |
| `{{time}}` | サーバーで設定したタイムゾーンでの通知の時刻 |
| `{{level}}`／`{{level_name}}` | 通知のレベルの数値／名前 |
| `{{event}}`／`{{origin}}` | 安定したイベントのキー／発生した場所の識別子 |
| `{{platform}}`／`{{adapter_id}}`／`{{account_id}}` | 出所のプラットフォーム／アダプター ID／ボットのアカウント |
| `{{group_id}}`／`{{group_name}}` | 出所のグループ ID／グループ名 |
| `{{user_id}}`／`{{user_name}}` | 出所のユーザー ID／ニックネーム |

システムのイベントにはグループ、ユーザー、出所のアカウントがない場合があり、その場合は値が空になり、身元を作り上げることはしません。変数は 1 回だけ置き換え、スクリプトを実行したり、通知の本文にたまたま現れたプレースホルダーをさらに解析したりはしません。URL、リクエストヘッダー、JSON のオブジェクトのキーは置き換えの対象外です。

リクエストボディのテンプレートは 64 KiB 以内の JSON オブジェクトで、入れ子は最大 16 段、描画後は最大 256 KiB です。リクエストヘッダーは文字列の値だけに対応し、改行を含めたり、Host や Content-Length などの保護された項目を上書きしたりすることはできません。Webhook のアドレス、署名の秘密鍵、カスタムのリクエストヘッダー、リクエストボディ内の認証情報は一覧の検索の対象外で、権限が制限された管理者が見るときは伏せられます。

WeCom の文章がサービス提供者の長さの上限を超える場合は安全に切り詰め、完全な内容は監査の詳細で確認できます。Webhook の HTTP のエラーや、プリセットのサービス提供者が返した失敗の状態はローカルのログに記録し、「リクエストを送った」ことを正常に届いたこととは見なしません。

ウィンドウをテストするときは、そのウィンドウに設定した送信用のアカウントや経路だけを試し、旧ルールにもともとほかの受信の経路が含まれていても、ついでにそちらへ送ることはありません。手動のテストではウィンドウの一時停止や日常のイベントの購読を無視できますが、全体のテストでは引き続き有効なルールだけを使います。テストで購読が変わることはなく、プラットフォームで最終的に届いたことの保証にもなりません。

## 監査ログ

すべての通知のイベントは `data/audit/notice_*.jsonl` に永続的に保存され、時刻、レベル、イベント、発生した場所、内容をさかのぼって確認できます。通知は、それを生み出した同じチャットには送り返さず、コマンドの返信と重複しないようにしています。配信は変更後の購読に従い、閉じたウィンドウが自分自身に関する通知のために一時的に復活することはありません。

表の各行は高さが固定で、長い内容は 1 行で省略され、内容をクリックすると詳細のダイアログが開き、本文全体とイベントの情報を確認できます。狭い画面では表を横にスクロールでき、見出しが 1 文字ずつ折り返されることはありません。

同じ出所の同じ種類のエラーは短時間のうちにまとめ、ほかのグループやプラグインの新しいエラーを隠すことはありません。通知ウィンドウ自体に届かない場合はローカルのエラーログに記録するだけで、自分自身の失敗の通知を生み出すことはできず、際限のない入れ子を防いでいます。プラットフォームの詳しい理由はローカルの構造化ログに残ります。

テンプレートの完全な確認用の原稿はメインのプログラムのリポジトリの `docs/notification-templates.md` にあり、実行の条件、レベル、文面、情報が欠けているときの扱いを 1 つずつ記載しています。

::: tip
通知ウィンドウを設定しているかどうかに関係なく、イベントは監査ログに書き込まれます。ウィンドウと送信が決めるのは、「誰かに能動的に知らせるかどうか」だけです。
:::
