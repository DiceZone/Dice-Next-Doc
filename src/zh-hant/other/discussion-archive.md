## 2026-08-11 · QQ 官方機器人 2.0 Webhook 接收模式（低優先順序）

### 結論

Webhook 可以與現有 QQ 官方機器人 2.0 適配器相容，程式碼實現屬於中等工作量，但使用者部署門檻明顯高於 Gateway WebSocket。當前 Dice!Next 使用者大多沒有公網 HTTPS 回呼地址，因此本項僅保留為低優先順序方案，不進入近期開發排期；預設接收方式繼續使用 Gateway WebSocket。

### Gateway WebSocket 與 Webhook 對比

| 對比項 | Gateway WebSocket（當前方案） | Webhook（候選方案） |
| --- | --- | --- |
| 公網入口 | 不需要，由 Dice!Next 主動連線 QQ Gateway | 必須提供 QQ 平臺可訪問的公網 HTTPS 地址 |
| 部署難度 | 低，家庭網路、動態公網 IP、內網環境均可使用 | 中高，通常需要域名、證書、反向代理或雲端中轉 |
| 連線維護 | 客戶端負責心跳、斷線重連、會話恢復 | 無長連線，但需處理回呼驗證、平臺重試和請求超時 |
| 事件結構 | QQ 2.0 標準事件 `op/t/d/id/s` | 與 WebSocket 使用相同事件結構，可複用現有事件分發 |
| 多賬號 | 每個適配器維護獨立 Gateway 會話 | HTTP 入口需根據受驗證的應用身份路由到對應適配器 |
| 重複事件 | 主要處理斷線恢復期間的重複推送 | 必須按事件 ID 去重，避免平臺重試導致指令重複執行 |
| 安全重點 | Token、Gateway 會話與連線狀態 | 原始請求體驗籤、時間視窗、防重放、限流和請求體大小限制 |
| 適用場景 | 普通使用者、本地部署、Docker、無公網環境 | 已有公網 HTTPS 服務、統一閘道器或對長連線有限制的部署環境 |

### 未來實現範圍

- 新增獨立的 Webhook HTTP 接收層，不復制 QQ 適配器的業務邏輯。
- 完成官方回呼地址驗證，並在解析 JSON 前按官方規則驗證原始請求體。
- 將 Webhook 與 Gateway 事件統一規範化後，交給現有 `dispatch()`、身份解析、指令、日誌及回覆流程。
- 支援多 QQ 官方機器人賬號的安全路由，不能只信任請求體中未經驗證的 AppID。
- 按事件 ID 設定帶有效期的去重記錄；快速響應回呼，再非同步處理可能耗時的指令。
- WebUI 增加“Gateway WebSocket / Webhook”接收方式與所需配置，並補充 HTTPS、反向代理及故障排查文件。
- 同一適配器預設只啟用一種接收方式；若未來允許雙通道容災，兩者必須共用事件去重機制。

### 工作量評估

- 最小可用版本：約 1～2 個開發日，覆蓋單賬號回呼、驗證、驗籤和現有事件分發複用。
- 可供公測的完整版本：約 3～5 個開發日，補齊多賬號、重試去重、WebUI、測試與部署文件。
- 自動申請域名、證書或內網穿透不建議納入主程式；若要內建此類基礎設施，預計需額外 1～2 周並引入持續運維成本。

### 啟動條件

出現明確的使用者需求，並且目標使用者具備穩定的公網 HTTPS 回呼能力；或 Dice!Next 後續提供獨立、可持續維護的雲端事件中轉服務。未滿足條件前不啟動實現。

## 2026-08-02 · 跨平臺身份與群資料關聯（討論草案，未確定）

### 討論目標

讓 QQ 官方機器人、Discord、KOOK 等平臺賬號，在驗證真實 QQ 控制權後，可關聯既有 `QQ:<真实QQ>` 與 `QQGroup:<真实群号>` 的歷史資料；保留舊插件對 QQ/群號主鍵的相容。

### 當前討論方向

- 骰主至少登入一次原 OneBot 骰號，儲存其可見的群列表、成員 QQ、群主/管理員角色與採集時間，作為歷史核驗快照。
- 使用者在新平臺發起繫結時，先宣告欲關聯的純數字 QQ 號。若 OneBot 線上，向該 QQ 私聊傳送短時、一次性驗證碼；若 OneBot 不線上，向對應的 `QQ号@qq.com` 郵箱傳送驗證碼。驗證碼成功僅證明使用者控制該 QQ 身份。
- 完成驗證後，將新平臺的“適配器 + 原始使用者 ID”作為別名關聯至 `QQ:<真实QQ>`，由統一身份解析讀取原有個人資料，而不是複製、拼接或覆蓋舊記錄。
- 已驗證的歷史群主可把其新平臺群關聯到歷史 `QQGroup:<真实群号>`：系統先核驗該 QQ 在 OneBot 歷史快照中是群主，再生成一次性群繫結碼，並要求在目標平臺的目標群完成確認。OneBot 線上時應優先重新整理角色快照；離線時只能使用帶時間標記的歷史核驗結果。
- 群關聯只繼承人物卡、團務、日誌關聯、規則/業務設定等資料入口；**不繼承**踢人、退群、管理員名單或舊群管理許可權。新平臺的管理操作始終遵從新平臺可讀取的當前角色；QQ 官方機器人無角色介面時，不補發群管許可權。
- 完全沒有 OneBot 的場景仍可使用虛擬 QQ/群主鍵與雙端一次性驗證碼建立邏輯關聯，但不能聲稱該邏輯群已核驗為真實 QQ 群。

### 尚待決定

- QQ 郵箱驗證碼的發件服務、限頻、失敗提示與是否要求 QQ 郵箱已啟用。
- 目標平臺無法讀取群角色時，是否允許已驗證歷史群主直接完成資料關聯，或要求骰主在 WebUI 額外確認。
- 兩端原本均已有個人/群資料時的衝突處理與可回滾合併流程。
- 歷史群主快照的有效期限、重新整理頻率及許可權變化後的處理。
