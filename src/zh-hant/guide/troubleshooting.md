# 故障排查

遇到問題時，按本頁順序排查。反饋問題時請儘量附上對應的日誌 / 崩潰報告檔案。

## 先找日誌

| 內容 | 位置 |
|------|------|
| 執行日誌 | `data/logs/app/dice-<启动时间戳>-<进程号>_<日期>.log`（每次啟動新建一份，跨天自動分割） |
| 結構化診斷 | 同目錄、同名 `.jsonl`，儲存處理來源、關聯 msgID、程式碼位置和執行緒等詳情；同樣脫敏 |
| 崩潰報告 | `data/logs/crash_<时间戳>.txt` |
| 跑團記錄 | `data/logs/`（`.log` 匯出的 txt / html） |
| 審計日誌 | `data/audit/`（通知系統的事件流水，jsonl） |

控制台視窗預設隱藏，可以從系統托盤圖示右鍵選單裡隨時顯示 / 隱藏。

首頁日誌預設 INFO，正常心跳與輪詢不會刷屏。需要排查時先在 WebUI 設定降低“最低記錄級別”，再降低首頁“最低展示級別”；後者無法恢復之前沒有記錄的除錯內容。傳送問題可按 msgID 檢視 `[处理]` 的來源、擬傳送內容與 `[消息]` 的實際內容及失敗原因，具體見[程式日誌](/zh-hant/manage/dashboard#程式日誌)。

## 程式閃退 /「已停止工作」

Dice!Next 內建崩潰診斷兜底：無論哪種崩潰（訪問違例、未捕獲 C++ 異常、CRT 無效引數、abort），退出前都會把死因寫到 **`data/logs/crash_*.txt`**，內容包括：

- 時間、崩潰型別、版本 / build 號
- **啟動階段標記**（`main:chdir` / `config` / `database` / `running` 等）——即使沒有堆疊也能知道死在哪一步
- 異常碼、出錯地址所屬**模組名 + 偏移**、未捕獲異常的 `what()` 文本

排查步驟：

1. 開啟 `data/logs/` 下最新的 `crash_*.txt`，看 `phase` 與 `kind`。
2. 再對照 `data/logs/app/` 裡同時間的執行日誌最後幾行。
3. 反饋問題時把這兩個檔案一起發給開發者，基本可以直接定位。

::: tip
若 `data/logs/` 目錄不可寫，報告會退而寫到程式目錄下的 `crash.txt`。
:::

## 雙擊 exe 後「什麼都沒發生」

這是正常現象：預設**啟動即最小化到系統托盤**（右下角會彈一個氣泡提示），不顯示控制台視窗。

- 在工作列右下角找托盤圖示，右鍵可「開啟網頁面板 / 顯示控制台 / 開啟應用目錄 / 退出」。
- 想恢復「啟動就顯示控制台」的舊行為：把配置 `dice.console_start_hidden` 改為 `false`。

## 第二個程序一啟動就退出

同一套資料（同一個 `data/` 目錄）**只允許執行一個程序**——啟動時會在資料目錄寫 `.instance.lock` 單實例鎖，檢測到已有實例時第二個程序直接退出，並在控制台/日誌裡給出提示，避免兩份程序同時寫資料庫造成損壞。

- 想跑多個骰子：複製一份完整程式目錄，各用各的 `data/`。
- 確認沒有其他實例卻仍提示被佔用：刪除資料目錄下的 `.instance.lock` 後重試。

## WebUI 打不開

1. **確認程序在執行**：托盤圖示是否存在；`data/logs/app/` 有無新日誌。
2. **埠可能變了**：預設埠 `18088` 被佔用時會**自動順延到下一個可用埠並寫回配置檔案**，啟動日誌會有一條 WARN。最簡單的辦法是托盤右鍵 →「開啟網頁面板」，它總是用當前實際埠；也可檢視 `config/server.json` 的 `port`。
3. **遠端訪問**：確認 `server.host` 為 `0.0.0.0`，並放行防火牆對應埠；不建議直接暴露公網，見[部署與運維](/zh-hant/guide/deploy)。
4. **提示需要登入**：設定過 WebUI 登入密碼後，所有後臺頁面都需要先登入；登入時勾選“信任此裝置”可在本機保留 30 天會話。

### 忘記 WebUI 登入密碼

停止程式，編輯 `config/webui.json`，刪除 `password` 欄位（或改為空字串 `""`），再啟動即可（空 = 關閉登入鑑權，記得重新設定）。

## 適配器連不上

先分清正向 / 反向：

| 模式 | 誰連誰 | 端點怎麼填 |
|------|--------|-----------|
| 正向 WS（`forward_ws`） | Dice!Next **主動連線** OneBot 客戶端 | OneBot 客戶端的正向 WS 地址，如 `ws://127.0.0.1:3001/` |
| 反向 WS（`reverse_ws`） | OneBot 客戶端**反連** Dice!Next | 只填一個**埠號**（如 `6700`），然後在 OneBot 客戶端把反向 WS 地址指向 `ws://<Dice!Next 所在 IP>:<该端口>/` |

逐項排查：

- **OneBot 客戶端**（NapCat / Lagrange / LLOneBot 等）是否開啟了對應的服務（正向 WS 服務端 / 反向 WS 上報），埠是否一致。
- **`access_token`** 兩端是否一致（留空則兩端都留空）。正向連線時 Dice!Next 會以 `Authorization: Bearer <token>` 頭髮送。
- **防火牆**：反向模式要放行 Dice!Next 監聽的埠；正向模式要能訪問到 OneBot 客戶端的埠。
- **狀態顯示「連線超時」**：正向 WS 斷線後會自動重連（前 10 次每 5 秒、第 11~20 次每 60 秒），連續 20 次失敗後暫停自動重連並置為「連線超時」——修好 OneBot 端後在適配器管理頁點手動重連即可。
- 儀表盤即時日誌與 `data/logs/app/` 裡有具體錯誤原因。

## 指令不回

- 群裡是否發過 `.bot off`（群停用）？在 [群組管理](/zh-hant/manage/groups) 或群裡 `.bot on` 恢復。
- 是否開了全域性靜默 / 全域性停用指令（[系統設定](/zh-hant/manage/settings)）？
- 使用者 / 群是否在黑名單裡？
- 白名單模式（`dice.whitelist_only`）下，不在白名單的群不會響應。
- 適配器狀態是否為「已連線」？
- 不想連 QQ 除錯：用管理面板的**測試臺**直接發指令看回復。

## 還是沒頭緒？

帶上以下資訊反饋：

1. 版本 / build 號（管理面板「關於」頁或啟動日誌第一行）
2. `data/logs/app/` 最新日誌的相關片段
3. 若是崩潰：`data/logs/crash_*.txt` 全文
4. 復現步驟
