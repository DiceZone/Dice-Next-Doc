# 雲服務與身份繫結

`.cloud` 是賬號中心授權的入口，`.bind` 負責把不同平臺的視窗關聯到同一個真實 QQ。
只繫結賬號時，用 `.bind qq <你的QQ号>` 即可，機器人會自動選擇核驗方式，不需要先學會郵件或 OAuth 指令。
需要雲人物卡時再使用 `.cloud`：雲卡授權也可以順帶核驗真實 QQ，而單純的繫結授權不授予雲卡讀寫許可權。

## 為什麼需要繫結

骰娘在不同平臺拿到的是不同的標識：OneBot 給的是真實 QQ 號，QQ 官方機器人只給一串
隔離的 OpenID，Discord 與 KOOK 各有自己的使用者 ID。沒有繫結時，同一個人在這些視窗
裡會被當成不同的人，人物卡、好感、屬性各存一份。

繫結之後它們指向同一份資料：在官方群裡錄的卡，回到 OneBot 視窗照樣能用。

## 繫結快速上手

在 QQ 官方機器人、Discord 或 KOOK 的**私聊**中傳送：

```text
.bind qq 160703953
```

把示例號碼換成你自己的 QQ。機器人會根據**當前客戶端**的配置自動選擇：

- **有正式骰娘 key**：優先 OAuth，私發賬號中心的授權網址和授權碼。在網頁登入並同意 QQ 身份核驗，回到原私聊傳送 `.bind confirm`。
- **沒有 key，但骰主啟用了 SMTP**：自動傳送驗證碼到 `你的QQ号@qq.com`，回到原私聊傳送 `.bind confirm <8位验证码>`。無需重新填寫 QQ 號。
- **兩者都未配置**：明確提示暫不可用，不發郵件、不完成繫結；可聯絡骰主設定，或從 OneBot / Milky 反向繫結。

OAuth 授權賬號的已驗證 QQ **必須與申請的目標號碼一致**；號碼不同、沒有授予身份許可權或賬號已經繫結其他 QQ，都不能覆蓋繫結。
OAuth 失敗時不會悄悄改成郵件；如骰主已配置 SMTP，可主動輸入 `.bind qq 160703953 email` 切換。切換後用郵件驗證碼確認，舊 OAuth 申請作廢。

申請與確認須來自同一個平臺原始使用者、同一個客戶端的同一私聊。機器人重啟或申請過期後，請重新發起。

## 雲人物卡快速上手

在**私聊**中對骰娘傳送：

```text
.cloud auth
```

骰娘會私發一個網址和驗證碼。開啟網址、用賬號中心的賬號登入、核對是哪臺骰娘在申請、
同意授權，然後回到私聊：

```text
.cloud confirm
```

看到“授權已就緒”即完成。若回覆中帶有你的 QQ 號，說明真實 QQ 已核驗並完成繫結。

::: tip 為什麼授權就能證明 QQ 號
賬號中心註冊時只接受純數字 QQ 郵箱，且必須通過郵件驗證碼。因此註冊郵箱的字首就是
一個已驗證的真實 QQ 號。
:::

## `.cloud` 指令

所有 `.cloud` 指令都只能在私聊中使用。

```text
.cloud auth [write] // 申请账号中心授权，默认只读，加 write 同时申请写入
.cloud confirm // 在网页输入验证码同意后，回到私聊确认
.cloud status // 查看当前授权状态
.cloud logout // 清除本机授权
.cloud list // 查看云端人物卡
.cloud pull <云卡ID> [本地卡名] // 拉取云卡到本地
.cloud push <本地卡名> // 首次上传本地卡
.cloud sync <本地卡名> // 按上次同步的版本提交
.cloud diff <本地卡名> // 只读对照基础、本地与云端字段，不改卡或同步基线
```

### 讀與寫

同步衝突時先用 `.cloud diff 本地卡名`：每項按“基礎 | 本地 | 雲端”排列，`local` 是僅本地修改，`remote` 是僅雲端修改，`same` 是兩邊修改一致，`conflict` 是兩邊不同修改。最多顯示 30 項；長值可用 `.cloud pull 云卡ID 新卡名` 拉取獨立副本對照。這個入口僅供本人私聊，不會繞過讀鎖，不會覆蓋卡或推進同步基線。

自動同步與逐欄位衝突編輯仍在設計中，尚未啟用；當前授權不意味著同意自動上傳，令牌過期或重啟後仍需重新授權。

預設只申請讀取許可權。需要上傳或同步時用 `.cloud auth write`，網頁上也必須明確勾選
寫入，兩邊都同意才生效。已經授權過只讀時，直接再執行一次 `.cloud auth write`。

### 授權的範圍與有效期

| 專案 | 說明 |
| --- | --- |
| 作用範圍 | 按“適配器 + 骰娘賬號 + 平臺 + 你本人”區分，與群無關 |
| 多個適配器 | 同時用 OneBot 和 QQ 官方時，兩邊各需授權一次 |
| 有效期 | 令牌只存在記憶體中，骰娘重啟或令牌過期後需重新授權 |
| 本地資料 | 重新授權不影響已拉取到本地的卡片與同步對映 |

::: warning 授權後骰主能看到什麼
同意授權即允許該骰娘讀取你在賬號中心註冊時驗證的 QQ 號。骰娘多由第三方自行部署，
部署該骰孃的骰主可以檢視這個號碼。不希望如此時，請在賬號中心的「已授權骰娘」中
撤銷授權。
:::

### 驗證碼

授權碼由骰娘單獨私發，不經過普通回覆日誌、AI 加工、插件、模擬聊天或跑團日誌落庫。
不要轉發驗證碼，也不要替他人完成授權。

## `.bind` 指令

```text
.bind // 查看完整用法
.bind qq <真实QQ号> // QQ 官方 / Discord / KOOK 私聊发起，自动选择 OAuth 或邮件
.bind confirm // OAuth：网页同意授权后，在申请的同一私聊确认
.bind confirm <8位验证码> // 邮件：在申请的同一私聊提交验证码，无需重填 QQ
.bind qq <真实QQ号> email // 主动选择或切换到邮件验证，需要骰主启用 SMTP
.bind qq QQ-Official-<机器人ID>:<OpenID> // 在 OneBot / Milky 窗口执行，关联官方用户
.bind qqgroup QQ-Official-<机器人ID>:<群OpenID> // 在目标 OneBot / Milky 群内执行，需要群主或管理权限
.bind discord <用户ID> // 在 OneBot 窗口执行
.bind kook <用户ID> // 在 OneBot 窗口执行
.info [qq|qqgroup] // 查看当前窗口的用户或群标识与已绑定端点
```

繫結某個平臺賬號之前，對方需先在該平臺向骰娘傳送過一條訊息——骰娘只能繫結自己
見過的標識，不能憑空寫入一個 OpenID。

`.bind confirm` 由服務端儲存的申請決定核驗方式：OAuth 申請不接受郵件驗證碼，郵件申請則必須填寫驗證碼。
舊寫法 `.bind email <QQ>`（主動申請郵件）與 `.bind qq <QQ> <验证码>`（郵件確認）仍保留相容，但不再作為主要教學用法。

反向繫結與郵件/OAuth 流程是不同入口：

- 官方使用者先在官方機器人私聊中用 `.info qq` 取得 `QQ-Official-机器人ID:OpenID`，再在**自己真實 QQ 的 OneBot / Milky 視窗**執行 `.bind qq <该标识>`。
- 官方群用 `.info qqgroup` 獲取群標識，在**目標真實 QQ 群**內由群主或管理執行 `.bind qqgroup <该标识>`，不能在私聊中證明群歸屬。
- Discord / KOOK 使用者先向機器人發過訊息，再在自己真實 QQ 的 OneBot / Milky 視窗執行 `.bind discord <用户ID>` 或 `.bind kook <用户ID>`。

### 幾種核驗方式的區別

| 方式 | 適用視窗 | 如何證明 |
| --- | --- | --- |
| 賬號中心授權 | 任意視窗（私聊授權） | 賬號中心已驗證的註冊 QQ 郵箱 |
| OneBot 會話 | OneBot / Milky | 協議端直接提供已驗證的真實 QQ |
| 群主或管理身份 | 目標群內 | 繫結群標識時額外核查發起人許可權 |
| QQ 郵箱驗證碼 | QQ 官方 / Discord / KOOK 私聊 | 接收目標 QQ號@qq.com 的驗證碼，並在申請的同一私聊提交 |

頭像核驗已棄用，不再要求使用者更換頭像。郵件驗證只用於使用者賬號，不證明群歸屬。

### QQ 郵箱驗證碼

骰主須先在「系統設定 → QQ 郵箱繫結驗證」填寫 SMTP 伺服器、埠、賬號、密碼或授權碼與發件郵箱，並啟用功能。
這是全域性配置，與「通知設定」中的郵件推送獨立；收件地址固定由目標 QQ 號生成，不接受任意郵箱。

- 通常 465 埠開啟隱式 TLS，587 埠關閉該項並強制 STARTTLS。伺服器必須具有有效證書，不支援明文認證。
- SMTP 密碼儲存後不回顯；編輯設定時留空會保留原密碼。
- 驗證碼有效 10 分鐘，連續錯誤 5 次失效；重發後舊碼失效，骰娘重啟後須重新申請。
- 每個平臺身份和目標 QQ 每小時各最多傳送 5 次，兩次傳送至少間隔 60 秒；全域性最多每小時 100 次。
- 驗證碼必須在原私聊提交，不能跨使用者、跨客戶端或跨目標 QQ 使用。驗證碼指令不進入插件、AI、模擬聊天與跑團記錄。
- 已繫結其他 QQ 的平臺賬號不能通過郵件流程覆蓋繫結。

郵件驗證不會授予雲人物卡訪問令牌；需要雲服務時仍使用 `.cloud auth`。不要替他人收取或轉發驗證碼。

`.bind` 的 OAuth 核驗也只申請郵箱身份許可權，成功或失敗後丟棄核驗令牌。它不等於 `.cloud auth` 的雲卡授權。

## 雲端人物卡

拉取後的雲卡是一張普通的本地卡：在跑團群裡用 `.pc tag <本地卡名>` 繫結，之後
`.st`、`.ra`、`.sc` 以及 Lua / JS 插件讀卡都照常工作。普通擲骰與改卡不發任何網路
請求，斷網、退出授權或雲端異常都不影響本地跑團。

同步是手動的，沒有後臺自動同步。

### 衝突與保護

- 上傳攜帶真實的基準版本號。雲端已被他人改動時返回衝突，骰娘不會重試、也不會強行
  覆蓋，雙方資料都保留。
- 拉取不會覆蓋已修改的本地卡。可以用 `.cloud pull <云卡ID> <新名>` 另存一份對照。
- 本地改名後仍寫回同一張雲卡；自選的本地別名不會在首次同步時覆蓋雲卡名。
- 同名的歷史多行、空名卡、未知 Schema、越界數值會被明確拒絕，不會猜一條上傳。

### 撤銷

`.cloud logout` 只清除本機儲存的臨時憑據。要完整收回授權，請到賬號中心的
「已授權骰娘」頁面撤銷。

## 骰主需要做的準備

玩家能用雲卡之前，骰主需先在賬號中心驗證骰娘所有權，並在
[雲服務 → 骰娘金鑰](/zh-hant/manage/cloud-services#骰娘金鑰)為當前適配器填寫正式 API Key。
自動申請的未驗證心跳憑據不能用於雲卡。該金鑰不要發給玩家。
