# 常见问题 FAQ

这里收集首次使用、日常维护与恢复配置时常见的问题。程序无法启动、适配器断线或指令没有回复时，也可查看[故障排查](/guide/troubleshooting)。

## 忘记管理面板密码怎么办？ {#reset-password}

需要能访问服务器上的配置文件。托管用户没有文件权限时，请联系托管方处理；QQ 骰主账号、适配器 Token 和 WebUI 登录密码不是同一个凭据。

1. **先限制管理面板的外部访问**，例如暂时关闭反向代理入口或仅允许自己的 IP。重置后会开放首次设置密码的入口，应避免被他人抢先设置。
2. 停止 Dice!Next；若由服务或守护进程管理，也要停止该服务，确认它不会立即重新拉起程序。
3. 备份实际使用的配置目录。默认是 `config/`，自定义路径或容器挂载位置见[下文](#config-location)。
4. 用文本编辑器打开 `config/webui.json`，只把顶层 `password` 的值改成空字符串：`"password": ""`，保留其他字段。不要把整个文件替换成这一小段。
5. 删除同一配置目录内的 `webui_sessions.json`（如果存在），撤销已保存的可信设备会话；不要把旧会话文件恢复回来。
6. 启动程序，通过受限入口打开面板，在首次设置页面设置新密码。密码须为 **8–64 位**，包含大写字母、小写字母、数字和半角特殊符号，不含空格、中文或全角字符。
7. 确认新密码可以登录后，再恢复正常访问入口。

**空密码会要求重新设置密码，不是免登录模式。** 配置里的密码可能是哈希，不必尝试还原或手工生成；让设置页面保存新密码即可。此次操作不需要删除数据库、人物卡或插件。

## 勾选了“信任此设备”，为什么还要登录？ {#login-session}

密码登录的可信会话最长保留 30 天，需要浏览器 Cookie 和服务器的 `config/webui_sessions.json` 同时存在。请检查：

- 是否换了浏览器、无痕窗口或访问域名（`localhost`、`127.0.0.1` 和自己的域名不是同一地址）。
- 浏览器是否清除了 Cookie，或设置了关闭时清除网站数据。
- 配置目录是否可写、会话文件是否被删除，以及服务重启后是否仍使用同一配置目录。
- 是否修改过密码或主动退出登录；这些操作会使相应会话失效。

第三方账号登录有自己的会话规则，不要把密码登录的 30 天规则套用于所有登录方式。

## 配置文件到底在哪？ {#config-location}

正常使用发行包管理器启动时，默认在安装目录的 `config/`。启动日志会显示实际读取的配置目录。如果服务启动参数指定了其他配置目录，以该路径为准；相对路径要结合进程的工作目录判断。

容器内的 `config/` 对应宿主机的挂载目录或卷，需要查看自己的 Docker / Compose 配置。不要只改临时容器里的另一份文件。多个骰子实例应分别使用自己的配置目录、数据目录和监听端口。

| 想修改的内容 | 默认文件 |
| --- | --- |
| 面板监听地址、端口、数据库路径、日志级别 | `config/server.json` |
| 面板密码及界面设置 | `config/webui.json` |
| 平台连接、适配器参数 | `config/adapters.json` |
| 骰主、指令、回复行为与 AI 配置 | `config/dice.json` |
| 好友与群邀请策略 | `config/events.json` |
| 默认回复语言 | `config/i18n.json` |

文件完整字段见[基础配置](/config/basic)。人物卡、跑团记录等并不全在这些 JSON 中；备份时也需要数据文件。

## 怎样手动修改配置？ {#edit-config}

优先使用面板；面板无法打开或需要恢复设置时，再编辑文件：

1. 停止程序及自动拉起它的服务，备份原文件到配置目录之外。
2. 用文本编辑器以 **UTF-8** 保存，保留原有结构，只修改目标字段。
3. 检查 JSON 格式：键和字符串使用英文双引号；不能写注释或尾随逗号；布尔值写 `true` / `false`，端口等数字不要加引号。
4. 启动程序，检查配置加载日志，再确认页面或指令中的实际效果。失败时停止程序，恢复备份文件后重新启动。

例如，修改 `config/server.json` 内的端口为数字 `18089`。该文件里直接使用 `"port": 18089`，**不用**再套一层 `"server": { ... }`。`adapters.json` 的顶层是数组，不能照搬其他文件的对象结构。

不要删除整个配置目录来“重置一个设置”，也不要把网上的完整示例覆盖到现有文件。手动配置备份请放在目录外，避免 `.json` 备份被当作新的配置区读取。

## 改了文件却没生效，或重启后又变了？ {#config-not-applied}

- 先确认改的是当前实例实际使用的文件，且保存成功、运行账号有写入权限。
- 程序运行时，面板保存、指令或其他配置写入可能覆盖手工编辑。停止程序后修改更可靠。
- 支持热重载不等于所有设置都能立即生效。**监听地址和端口需要重启**；其他设置不确定时也应安排重启验证。
- 有分适配器、分账号或群设置的功能，可能覆盖全局默认值。回到对应作用域检查，不要反复修改全局值。
- JSON 解析或校验失败时，先看启动日志中的具体文件与错误；不要假定修改已经加载。

## 本机能打开面板，另一台设备打不开？ {#panel-access}

另一台设备上的 `127.0.0.1` / `localhost` 指向它自己，不是骰娘服务器。应访问服务器的实际地址和端口，并检查监听地址、防火墙与云服务器安全组。

默认端口是 `18088`，被占用时可能顺延，以启动日志或 `config/server.json` 为准。用域名反代时，代理目标端口也要同步修改。部署 HTTPS 和反向代理见[部署与运维](/guide/deploy)。

## 备份和换服务器要带哪些文件？ {#backup}

建议先在面板制作备份，检查备份所选项目，尤其是插件、牌堆、图片和媒体是否包含在内，并把备份下载到另一台设备。

手动备份时，**停服后**复制实际使用的配置目录和整个 `data/`，同时保存放在这些目录以外的自定义插件、资源及数据库。自定义数据库位置以 `server.json` 的 `db_path` 为准。运行中只复制一个 `.db` 可能遗漏尚未写回的数据。

换服务器先安装对应操作系统和架构的完整发行包，再恢复配置与数据；不要把 Windows 可执行文件直接搬到 Linux 使用。启动前检查绝对路径、文件权限、端口和适配器地址。旧服务器先停服，避免两边同时登录或处理同一批消息。旧 Dice 的数据请使用[迁移工具](/guide/migration)，不要直接覆盖 Next 数据库。

## 升级后页面空白、404 或样式不完整？ {#webui-update}

先确认打开的是正确实例和端口，尝试刷新页面。若持续失败，检查是否只更新了可执行文件而遗漏 WebUI：应使用同一版本的完整发行包，包含 `web/dist/`、运行库及其他配套资源。不要混用不同版本的前后端，也不要用删除 `config/` 或 `data/` 的方式排查。

手动修复前停服并备份，再按[完整升级步骤](/guide/install#升级)更新程序文件。反向代理部署还应检查静态资源请求是否被错误缓存或转发到旧实例。

## 为什么无法自动安装更新？ {#auto-update}

完整安装需要通过发行包管理器启动：Windows 使用 `dice-next.exe`，Linux/macOS 使用包内的 `start.sh` 或 `dice-next`。直接运行 `dice-next-server` 仅能检查和下载。容器内只检查和通知，请更新镜像并重新创建容器。

下载失败时查看页面提供的错误，检查来源可达性、磁盘空间与写入权限；可尝试内置镜像或 GitHub。不要关闭校验来强行安装不完整包。定时安装使用服务器设置的时区；自动安装开启且包已就绪时，提前重启也会安装，详见[更新设置](/manage/settings#检测与自动更新)。

## 已连接却不回指令，怎么区分问题在哪？ {#no-reply}

先发一条简单的 `.r 1d6`，查看首页运行日志：

- **没有收到消息的记录**：检查适配器登录、事件订阅和平台消息投递；QQ 官方平台可尝试 `/r 1d6`，并检查自己设置的指令前缀。
- **收到但没有回复**：检查群内 `.bot off`、全局静默、禁用指令、黑白名单及插件规则。
- **已生成回复但发送失败**：看平台返回的具体错误，检查账号是否仍在群里、是否有发送权限及内容是否被平台拒绝。

可在[测试台](/manage/playground)验证指令本身，但测试台成功不代表真实平台一定能投递消息。回复格式、按钮和图片的支持也因适配器而异。

## 反馈问题时应该提供什么？ {#report}

提供版本号、操作系统、适配器类型、发生时间、复现步骤、预期和实际结果，并附上同一时段的相关日志；崩溃时加上崩溃报告。日志位置见[故障排查](/guide/troubleshooting)。

发出前检查并遮盖密码、Token、API Key、AppSecret、会话文件内容及不相关的私人聊天。**不要公开上传整个配置目录或数据库**。只说“没反应”很难定位；一条可复现的指令和对应日志通常更有效。
